# Making teaching software keep its promises

I spent the day tightening the rules behind [Peptidyle](https://github.com/vosslab/peptidyle-learning-engine), my mastery-teaching platform: who can publish a question, what a question's identity means after it changes, and which tests prove real behavior instead of preserving yesterday's setup.

## A question needs a history

In a mastery system, students may see several versions of a problem before they can reliably solve it. That makes question editing less casual than it sounds. If I correct a prompt after students have used it, I need the software to preserve what they actually encountered.

I separated ordinary publication from an original owner's correction. A correction keeps the existing Question ID, archives the replaced version, and moves future assignment definitions forward. The point is historical honesty. A grade or attempt should remain tied to the question a student saw, even when its author later fixes a mistake.

I also replaced visible numbered and versioned identities with non-sequential Question IDs. They are validated on the server and designed to remain identifiers rather than becoming a tiny public record of every revision. The system has a defined ceiling of 100 million questions, which makes the constraint explicit instead of leaving it as an assumption buried in code.

The same cleanup reached roles. Peptidyle now has three human roles: Student, Instructor, and Sysadmin. Instructors and sysadmins may publish; students may not. I wrote one canonical role document because permissions become fragile when their explanation is scattered across source files, test names, and old notes.

## Tests should protect people, not furniture

I removed ten quick Python tests. That sounds backwards until the tests are examined.

They were checking the current shape of shell scripts, container files, reverse-proxy configuration, SQL strings, and dated walkthrough material. Those checks could fail when I made an ordinary implementation change, even if the application still behaved correctly for students, instructors, and operators. They protected repository furniture.

I kept the security boundary intact while repairing browser regressions. For example, a course-banner test now requests an asset through the protected delivery endpoint before loading it. The test exercises authorization as a browser does, rather than reaching around the rule it is supposed to verify.

I also made completion evidence more explicit. A development goal is not complete merely because a convenient set of tests passes. Its required permanent tests, integration checks, live checks, acceptance evidence, and independent review now belong to the goal itself. That distinction helps me avoid calling a feature finished while an important kind of evidence is still absent.

## Building an instructor interface for actual work

I continued building the instructor side of Peptidyle around an ordinary 1280-by-800 screen. Instructors need to see assignments, question libraries, rosters, and grades without spending the day opening and closing oversized panels. Students, meanwhile, need a responsive question experience that works on smaller screens.

I assembled a 13-page visual corpus around one simulated course. It includes the course list, assignment screens, roster, gradebook, library, question editor, workspace, and account settings. Reviewing those pages together is more useful than judging isolated mockups. A gradebook may look fine alone while becoming impractical once the surrounding navigation, filters, and course context are present.

Shared spacing and density rules now keep the shell and page content coherent. I retained each course's three-color palette anchors, then derived the rest of the interface from a common recipe for canvas, work areas, reading cards, text, and actions. That lets courses remain distinct without making each screen a separate design system.

Accessibility remains part of the standard view: semantic structure and a 5.5:1 ordinary-text contrast target. I did not treat accessibility as a reason to turn every instructor page into a large, low-density display that makes real academic work harder.

I also added a small Python controller for the rootless local Podman stack. It can inspect the local environment, report status, show scoped logs, and handle normal lifecycle tasks. That replaces a private sequence of shell commands with an understandable tool.

## One useful pattern beyond Peptidyle

I saw the same problem in [vosslab-skills](https://github.com/vosslab/vosslab-skills), where I reorganized the public skill library into six categories: orient, plan, manage, experts, docs, and quality. The repository now enforces that structure, regenerates its indexes and plugin manifests, and validates the skill folders. Plain `pytest tests/` passed all 2,872 tests, with six advisory or dependency warnings.

Across both projects, I was trying to make the intended path obvious: one authority model, one durable identity, one meaningful test boundary, and one place to look when something needs attention.
