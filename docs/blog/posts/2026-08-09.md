# Making Course Imports Accountable
<!-- more -->

Today I finished a QTI import path for the [Peptidyle Learning Engine](https://github.com/vosslab/peptidyle-learning-engine). The visible change is an upload panel for authors. The important change is that imported course material now enters through a narrow, traceable process instead of becoming a second, loosely defined authoring system.
## I imported questions, not an entire platform

Peptidyle is built for mastery learning: students should be able to retry varied problems, keep practicing after they meet a goal, and never receive answer keys or grading logic in the browser.

That makes imports useful but risky. Canvas and Blackboard course exports can contain valuable questions, but they also carry assumptions and features from systems I am not trying to reproduce. I wanted authors to bring over the questions Peptidyle can support faithfully while keeping validation, grading, publishing, and storage under Peptidyle's control.

I completed the author-facing QTI import panel in the existing workspace, alongside the ordinary editor rather than in place of it. It uses the same site and the server contracts already accepted by the application. That was deliberately unglamorous: the interface is the last layer of a process designed to make imported material understandable and accountable.

## I kept the parser deliberately small

I did not build a general-purpose QTI importer. The current Blackboard Original QTI 2.1 path accepts a bounded set of static, single-choice questions. It retains certain harmless scoring declarations as source context, but it does not pretend every part of an exported package has a meaningful equivalent in Peptidyle.

That restraint matters. A broad importer can create a frustrating promise: it accepts a package, quietly drops unsupported behavior, and leaves authors with questions whose results are difficult to explain. I chose the opposite approach. The server recognizes the subset it can carry over correctly, rejects what it cannot support, and converts accepted questions through a server-only bridge into Peptidyle's existing question format.

This means an imported question must pass the same checks as a question created directly in the platform. I do not want imports to create a special class of content that every later feature has to handle differently.

## I treated provenance as part of the feature

The harder problem was not reading XML. It was preserving a trustworthy record of what an imported question came from.

For imported choice questions, I added a private, versioned mapping that records the order of answer choices in a fixed format and verifies it with a checksum. I bound the archived source package to that identity rather than treating the upload as an incidental attachment.

That decision continues through conversion and storage. A conversion is tied to the exact accepted source identity, and protected access to that provenance data is deliberately narrow. In plain terms, I wanted the system to be able to answer a practical future question: "Which source package and answer-choice mapping produced this item?"

A small checksum repair along the way was a useful test of that design. If a checksum is just decorative metadata, repairing it is routine bookkeeping. If it helps identify the exact mapping behind an imported item, it is part of whether the system can honestly claim that a conversion is reproducible.

The finished import flow keeps a bounded original ZIP package in private storage, queues one conversion job, produces a report, and only then coordinates publication. The upload panel is therefore not just a browser control for sending a file. It starts a process that ends with an accepted, reviewable item.

## I reinforced the same boundary elsewhere

I also tightened related security behavior. Learner-response recovery now uses browser session storage only and clears its active buffer when a learning run ends. File-upload answers fail closed until I can support them safely.

These are different features, but they follow the same rule: the browser can make a workflow convenient, but it should not quietly become the authority for protected state. Authors can begin an import in the browser; learners can recover in-progress work there. Source objects, grading, publication decisions, and durable records remain on the server.

I also refreshed the project's public status materials to distinguish what is implemented and verified from what remains a proposal. That distinction becomes more valuable as planning and implementation accumulate together.

The next work is not another import format. I have plans to make the platform calmer to operate and easier to present, including a small public landing site separated from the authenticated application and a more focused course-theme system. Before expanding the edges, I wanted the import path at the center to have clear limits.
