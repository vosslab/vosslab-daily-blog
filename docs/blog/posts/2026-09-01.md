# Refusing artifacts that only look right

A useful frustration connected today’s work: a program can make something that appears finished while missing the property that makes it usable. A rendered slide can resemble a deck but be a page-sized image. A tidy browser response can accidentally publish internal model details. OCR can return readable text without exposing the cleanup choices that changed it. The work across these projects was about turning those distinctions into executable boundaries instead of relying on visual plausibility or convention. <!-- evidence: ev-345261e887290b6a, ev-871c8c46baac7190, ev-e67e189ff94b4fec -->

## Slides should still be presentations

The clearest version of the problem was in [vosslab/marp-slides](https://github.com/vosslab/marp-slides). The project moved away from browser-rendered, flattened output and now treats repository-owned Python as the interpreter of authoritative Marp Markdown into editable PPTX objects. LibreOffice then creates editable ODP and PDF artifacts from that native path. A full-slide raster image is not a tolerated fallback; it is a failed presentation conversion. <!-- evidence: ev-871c8c46baac7190 -->

That is a narrower promise than “render Markdown into slides,” but it is the promise course material needs. A lecture deck is revised, annotated, copied into another unit, and repaired after someone notices an error. Text needs to remain text. Lists need to remain lists. Hyperlinks need destinations. Presenter notes, slide titles, component images, and image descriptions need real owners in the output document. A screenshot of all those things is not an editable presentation, however convincing it looks. <!-- evidence: ev-871c8c46baac7190 -->

The satisfying part is that the project checks those claims structurally rather than trusting a visual comparison. Its semantic end-to-end gate inspects generated PPTX and editable ODP files for text, lists, hyperlinks, notes, images, descriptions, slide counts, and the absence of page-sized full-slide images. That last check is especially useful because rasterization is the tempting shortcut that can make a failed conversion look successful. <!-- evidence: ev-871c8c46baac7190 -->

The migration evidence also pushed against an intuitive but incomplete definition of fidelity. While reconstructing a 31-slide course deck, structured extraction retained an estimated 99.6 percent of words, compared with 95.8 percent for OCR. The result makes sense once fidelity means preserving a usable document rather than preserving pixels: native structure left behind a deck a teacher could continue working with. <!-- evidence: ev-871c8c46baac7190 -->

The exporter is deliberately bounded. Marp Core v5 remains the authoring and conformance baseline, but accepted source features need credible native editable-output owners. Formatted runs, links, inline code, nested lists, directives, component images, blockquote-based multi-cell content, and presenter-note comments are supported. Tables and fenced or indented code instead fail at the source location; they are not silently approximated into a shape that looks complete while losing meaning. <!-- evidence: ev-871c8c46baac7190 -->

That boundary is backed by seventeen named layout builders, each responsible for geometry, reading order, and content regions. The exporter can reject content that would overlap, disappear, or exceed its assigned area. It applies the same rule to title sizing: a top-level title that cannot fit its bounded native region is rejected rather than quietly shrunk. The fast suite recorded 937 passes, and documented folder builds produced PPTX, ODP, and PDF artifacts for both canonical genetics decks. <!-- evidence: ev-871c8c46baac7190 -->

The remaining question has moved from output plumbing to source-language design. Top-level blockquotes currently carry multi-cell content in layout reading order. The first Marp+ milestone proposes explicit named `_cell` markers instead. The real test is whether that syntax can clarify author intent without weakening source-located diagnostics, defined reading order, native layout ownership, or the editable-output guarantee. <!-- evidence: ev-871c8c46baac7190 -->

## A browser reader should not inherit an internal object

In [vosslab/peptidyle-learning-engine](https://github.com/vosslab/peptidyle-learning-engine), the same refusal of plausible substitutes appeared as a vocabulary and boundary cutover. Terms such as `definition`, “version,” and provider keys had accumulated incompatible meanings across authored material, private drafts, immutable releases, browser data, adapter details, and operational records. That is not merely untidy terminology: it lets code treat related records as interchangeable when they have different owners and lifecycles. <!-- evidence: ev-345261e887290b6a -->

The current model makes several of those distinctions explicit. Immutable Blueprint Course revisions use `blueprint_content`; Question Model sources and private Draft Question Revisions use `question_content`; and “Question Version” becomes “Question Revision” to identify a frozen record. Authoring source, draft material, released content, and delivered content remain related, but they no longer have to masquerade as the same JSON with different names. <!-- evidence: ev-345261e887290b6a -->

`CourseAppearanceView` is the smallest, clearest public example. Its reader-facing shape is exactly `{ theme, revision, banner }`, and its banner is exactly `{ reference, alternativeText }`. Strict decoding rejects surplus fields, the retired banner `id`, invalid themes and revisions, and invalid alternative text. The reader uses no-store GET requests and requires a matching strong revision ETag. <!-- evidence: ev-345261e887290b6a -->

I find that kind of narrowness satisfying because it makes a small browser object carry a precise claim: the reader gets a reader view, not a convenient projection of an internal record whose incidental fields might become public commitments. Generated declarations, fixtures, decoders, browser checks, formatting, and diff gates all reinforce one shape rather than letting several near-equivalent representations drift apart. <!-- evidence: ev-345261e887290b6a -->

The stronger move is what the migration declines to preserve. There are no aliases, dual DTOs, retired wire properties, or legacy columns acting as soft compatibility layers. PostgreSQL acceptance lanes prove intended constraints and the absence of retired structures, while strict browser decoders reject obsolete shapes. If two representations can still claim to be current, the ambiguity has survived the migration. <!-- evidence: ev-345261e887290b6a -->

Course Appearance also leaves a useful unfinished edge. The revision-aware reader contract is complete, but durable write-side storage, an authoritative current-revision mechanism, PostgreSQL migration, server route, authorization oracle, upload promotion and cleanup, and a mounted editor remain deferred. The next proof is whether creating and promoting content can retain this discipline without rebuilding the parallel representations the read path just removed. <!-- evidence: ev-345261e887290b6a -->

## OCR recovery needs receipts

[vosslab/book-to-markdown](https://github.com/vosslab/book-to-markdown) approaches a similar problem from the opposite direction. Difficult PDFs now have an explicit qualified route: PDFs with genuine text layers use `extract/pdf_raw_text_extraction_to_markdown.py`, while scanned or degraded PDFs use the restored Tesseract entry point, `extract/pdf_to_markdown.py`. Both continue through cleanup and the preferred block-aware validator. “OCR completed” is not treated as proof that recovered Markdown is ready to deliver. <!-- evidence: ev-e67e189ff94b4fec -->

The restored OCR command is an adapter over the established extraction and cleanup pipeline, not a parallel recovery system with private semantics. It delegates OCR to `pdf_extract.ocr_text` and shares cleanup, evidence reporting, and removal tracking. A normal run produces cleaned Markdown, a JSON report, and a sidecar recording removed material; measure-only mode inspects extraction evidence without writing Markdown or a sidecar. <!-- evidence: ev-e67e189ff94b4fec -->

Those extra artifacts matter because cleanup makes judgments. A recurring header may be a running head worth removing; a page number might be noise; a seam might need joining; a dotted numbered line might or might not be a heading. The route exposes controls for retaining running heads, page numbers, seams, and dotted lines for A/B comparison, and it exposes thresholds for identifying running-head candidates. The result is a recovery path with strong defaults that still admits where source-quality judgment remains necessary. <!-- evidence: ev-e67e189ff94b4fec -->

The operational dependency is visible too: the usage guide puts `TESSDATA_PREFIX=/usr/share/tesseract-ocr/5/tessdata` beside the Tesseract invocation that needs it, and a CLI-contract test protects the entry point. The project has restored a supported route into its existing recovery workflow rather than leaving a difficult-PDF workaround for someone to rediscover later. <!-- evidence: ev-e67e189ff94b4fec -->

Automatic route selection or a unified PDF command may be worthwhile later. For now, the explicit opening question is valuable: does this source have usable text, or does it need recovery? That question keeps the user involved at the point where a plausible result could otherwise hide a consequential assumption. <!-- evidence: ev-e67e189ff94b4fec -->
