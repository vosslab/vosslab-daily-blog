# Making the Test Path Tell the Truth

The most useful realization today was that a browser test is only persuasive when it travels the same path as a real person: production bundle, real sign-in, connected services, and visible result. I spent the day making that path singular and accountable.
<!-- more -->
## One Browser, One Real System

Most of my attention went to [Peptidyle Learning Engine](https://github.com/vosslab/peptidyle-learning-engine), an open mastery-teaching platform where students work through varied problems while grading and answer keys stay on the server.

I retired the alternate test-only browser artifact, mock runtime graph, local-file authentication route, and several obsolete walkthrough lanes. Playwright, screenshot capture, direct browser development, and aggregate acceptance now share one disposable production HTTPS stack. That stack includes the real Rust API, PostgreSQL database, object storage, worker, renderer, account and session authentication, authorization, and seeded live-demo baseline.

This sounds like infrastructure cleanup, but it changes the meaning of a green test. A scenario can no longer quietly prove behavior in a substitute system. It either completes the connected workflow users receive or it fails where that workflow actually fails.

I also divided the browser-suite owner into explicit launch, visible-scenario execution, cleanup, receipt, and screenshot-transfer responsibilities. That makes failures more legible: startup, user journey, artifact publication, and teardown should not collapse into an opaque “browser test failed.”

The real UI journey exposed an important product boundary. An entitled learner without a materialized assignment receipt now gets a key-free, read-only `noActivity` view rather than a secretly created enrollment or a misleading empty assignment. Denied and unknown assignments remain concealed. But an existing enrollment missing its required summary remains a service failure—not something to disguise as normal absence. Privacy-preserving emptiness and broken persistence are different states, and the interface now respects that difference.

## Evidence That Can Catch a Timing Bug

I published a JSON-authoritative screenshot corpus from the production HTTPS origin, with role- and journey-specific captures across instructor and learner flows. The evidence process did its job: automated image review found that a saved course appearance was not visibly confirmed at the moment it should have been. After recapture, the confirmation and selected Forest theme were visibly present, and re-review closed the finding.

That is a small defect, but it captures why screenshots belong in the acceptance path. They are not promotional leftovers; they are evidence of what the system actually communicates at the point of use.

The final validation covered Rust checks, codebase checks, 6,417 pytest tests, production-browser scenarios at one HTTPS origin, WebWork checks, replica restart behavior, and exact cleanup receipts.

## Durable Authority in Chemical Documents

In [Ferrum Chemical Forge](https://github.com/vosslab/ferrum-chemical-forge), a Rust chemical-document tool for durable CDML records, I pursued the same concern from another direction: an action should have one durable owner.

Presentation and catalog IDs now come from `DocumentSession` transactions. Arrows, vectors, paths, and catalog insertions receive durable IDs only after a successful document mutation; previews, refused candidates, and failed preparation do not advance counters. The document session also owns authoring capabilities, preserving typed retry, rollback, replay, and foreign-session behavior without confusing temporary authorization with durable document state.

I made one corrective change that matters beyond this project: I removed an oxidation result from the atom-chemistry-facts contract because no public protocol, CLI, PyO3 binding, or Qt route exposed it. The contract should describe the reachable system, not the system I intend to build later.

[Track Runner Virtual Dolly Cam](https://github.com/vosslab/track-runner-virtual-dolly-cam) also received a six-audit cleanup that fixed one runtime seam and passed 3,885 tests. Meanwhile, [Battery Control](https://github.com/vosslab/battery-control) added 33 hourly operating-data rows through 22:00.

The open question is how far to extend this standard: where does any remaining shortcut still claim success before it has earned it?
