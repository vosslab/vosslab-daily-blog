# Making a learning engine safer to change

I spent most of today on [Peptidyle](https://github.com/vosslab/peptidyle-learning-engine), my mastery-learning platform. The work ranged from grading and enrollment to source-code maintenance, but it followed one practical idea: important systems need clear ownership boundaries before convenience hardens into risk.

<!-- more -->

## Keeping authority on the server

Peptidyle lets students retry varied problems until they can solve them consistently. That only works if the platform can keep a student's learning record trustworthy while protecting grading logic and answer keys.

I settled the direction for secure grading before the next release-candidate work. A learner's submitted work is now tied to an authenticated attempt and an idempotency key, rather than asking the server to trust a collection of browser-provided identifiers. The server keeps the durable identity of each answer choice private and issues a temporary, attempt-specific mapping for the browser to use.

That distinction matters. A radio button may look simple, but the browser should not get to name or control the underlying answer object. I want retries and replay protection to work reliably without treating the client as an authority.

I also added a defined internal JSON format for the question types Peptidyle needs: single and multiple choice, blanks, numerical answers, matching, ordering, and image-backed questions. The import pipeline, renderer, and grading code now have one shared shape to work from instead of accumulating special cases.

## Giving WeBWorK a clear job

I use WeBWorK and PG/PGML for rendering and grading serious mathematical and scientific questions. They are strong tools, but I do not want Peptidyle to become a second assignment platform wrapped around them.

The local development stack now uses the external `webwork-pg-renderer` image rather than treating the rendering engine as an internal subsystem. That makes the boundary explicit: `openwebwork/pg` handles PG and PGML rendering and grading; my private renderer bridge connects it to Peptidyle; Peptidyle owns the course experience, attempts, mastery model, and security rules.

This separation also makes failures easier to understand. A renderer outage should look like a renderer outage, not like an unexplained fault somewhere inside a large application.

I tested the upstream WeBWorK profile against the cases that matter during an active student attempt: cached renders, server-owned full and zero scores, replayed submissions, renderer outages, and persistence while offline. A polished demo would not have revealed those edges.

## Narrowing identity and enrollment

I also cut a design that was starting to grow without a clear need. While working on passwordless identity and enrollment, I explored a separate course-scoped account-recovery system. I rejected it.

Verified email is Peptidyle's actual registration and sign-in path. Passkeys are useful conveniences, but they should not become a separate source of account truth. The recovery proposal was beginning to add transfer rules, session distinctions, database structure, and web endpoints that the underlying identity model did not require.

Removing that unfinished foundation kept the identity work narrower. I am still working through roster locking and invitation flows, but those pieces now have a clearer purpose.

I also removed SMTP as a prerequisite for handing an individual invitation to an instructor. An authorized instructor can receive a short-lived, same-origin redemption link without weakening email authentication. That removes an operational dependency while keeping the security property intact.

## Making code size a real limit

In [starter-repo-template](https://github.com/vosslab/starter-repo-template), I added a test that allows source files up to 999 lines and fails at 1,000. It checks tracked authored files, so ignored local reference material stays out of scope while maintained code cannot quietly escape the rule.

The first run found four oversized files. I did not add exceptions. I split them by responsibility.

The repository reset script became a small command-line entry point, with separate modules for planning, file changes, and answers. Version management and package-publishing support received the same treatment. The full test suite passed after the work, and the largest remaining replacement module sits below the limit.

I applied the same pressure to Peptidyle, where 26 oversized maintained files were divided into smaller persistence, server, and application units. That work exposed a stale test filter in the disposable PostgreSQL setup: one integration path was not being exercised as completely as I expected. The refactor improved the shape of the code, but more importantly, it revealed a hidden gap.

By the end of the day, Peptidyle had firmer lines around what the browser can know, what the server must own, what WeBWorK is responsible for, and what each source file should contain. The secure-payload and enrollment work still need acceptance before I can call them complete, but the system is becoming easier to inspect and safer to change.
