# A Conversion Pipeline Needs a Chain of Custody

Today I spent time making [vosslab/vosslab-skills](https://github.com/vosslab/vosslab-skills) less eager to sound successful. Book conversion has enough moving parts that a plausible-looking result can hide a missing dependency, a discarded text layer, or a cleanup decision nobody can trace back to its source. I wanted the workflow to tell the truth about each of those cases.

## The log has to point to the thing it removed

<!-- evidence: ev-7848ff9440f18b3b -->

The most satisfying repair was a small-looking defect in `clean_markdown.py`: its audit sidecar was reporting removal locations relative to the current transformable chunk, rather than to the original document.

That distinction only shows up once the document gets interesting. The cleaner deliberately protects frontmatter, fenced and indented code, and blockquotes. It transforms the material around those protected spans, removing images and inappropriate HTML while preserving useful semantics. But if protected material came before a later removal, the sidecar’s line number could point a reviewer to the wrong place.

A removal log that cannot locate the removal is not much of an audit trail. It is a suggestion that something happened somewhere nearby.

I threaded each chunk’s absolute starting line through the transformation path, including the helpers for tables, MathML, SVG, figures, and superscript/subscript conversion. Then I added a fixture with protected material both before and after image and HTML removals. The test is intentionally ordinary: it checks that a person following the sidecar can find the original thing automation changed.

That gives the sidecar a more serious role. It is not debugging exhaust. It is a chain of custody for a document that has been altered by a heuristic.

## Recoverable is better than pretending to be perfect

<!-- evidence: ev-7848ff9440f18b3b -->

The line-number correction made a known edge case easier to describe honestly. The recurring-running-head cleanup can remove a legitimate heading when that heading has exactly the same text as a running head. `Preface` is the clean example: in the measured Springer case, it could recur across pages and look enough like boilerplate to trigger the removal rule.

There is a tempting response to a case like that: keep adding conditions until the failure disappears from the documentation. I do not think that is the right move yet. The evidence supports a narrower and more practical answer: record the removal precisely, document the edge case, and restore the heading from the sidecar when it occurs.

I enjoyed making that trade-off explicit. The goal is not a grand claim that the cleaner understands every book layout. The goal is a conversion workflow that can be trusted when it is right and repaired without archaeology when it is not.

## The source can disappear during conversion

<!-- evidence: ev-7848ff9440f18b3b -->

The sharper surprise came from DjVu. `ddjvu -format=pdf` looks like a convenient bridge into a PDF-oriented pipeline, but it can silently drop DjVu’s text layer. In the Tufte case I measured, the original DjVu contained 43,943 words of clean publisher text; the PDF produced by that conversion had zero words.

That is a nasty kind of failure because the resulting PDF does not announce that it has thrown away evidence. If I treated it as the source, I could conclude that the book required OCR and then spend time reconstructing text that was already available cleanly.

The workflow now starts with the original:

`djvutxt book.djvu | wc -w`

A text-bearing DjVu supplies clean non-OCR prose for the canonical body, while PDF-derived material can still contribute structure and captions. A textless DjVu is recorded as corroborating provenance instead of becoming a reason to run redundant OCR. The lesson was specific enough to stick with me: measure a source before transforming it, because the transformation may erase the exact property you needed to choose a strategy.

## State should be visible to the operator

<!-- evidence: ev-7848ff9440f18b3b, ev-576bff2b15e34153 -->

The surrounding fixes follow the same principle. Missing `pymupdf4llm` now produces an install hint. Missing Tesseract fails EPUB OCR once, before it emits a page-by-page trail of misleading errors. The skill documents its runtime dependencies, including the optional `djvulibre-bin` package, so provisioning is part of starting correctly rather than an after-the-fact deduction.

I also corrected `--measure`. It reports measurements; it intentionally does not write Markdown. It now says so rather than printing a `Markdown:` path for a file that does not exist.

This sounds minor, but conversion work has distinct states: measured, converted, validated, and delivered. When a tool blurs those states, downstream work is forced to infer reality from absent files and confusing errors. A good command-line interface does not merely report activity. It tells the operator what state it actually reached.

Validation got more exact as well. Semantic `<sub>` and `<sup>` remain valid because chemical notation and footnote markers can need them. Layout HTML such as `<div>` still fails delivery validation. Structured inputs—DOCX, EPUB, HTML, and ODT—skip the PDF-style bare-page-number check, where lone numbers can be meaningful content rather than extraction debris. Archive output now names its completed state `COMPLETED_SOURCE`, alongside folders for sorted Markdown, duplicates, and remaining work.

The remaining question is whether structural cues can eventually separate a genuine heading from an identically worded running head more selectively. I do not have enough evidence to broaden that rule yet. For now, I am happier with the smaller promise: preserve the evidence, say what happened, and leave a reliable route back when automation reaches its boundary.
